## 2026-11-02 (15) — Big build in parts A-C (all visuals need screenshot / phone review)
### PART A — flicker fix, dynamic nails/claws, glove cards, length-aware items + webbing
- FLICKER: cause was the "which side faces the camera" flag (tracker left/right label + knuckle geometry flip frame to frame, so back-only nails appeared and vanished). `HandDynamics.stableBack` (js/dynamics.js) now holds the side until the other one is seen 6 frames in a row; the dynamic "shown" flag has hysteresis (on above 0.22, off below 0.08) and the stretch is smoothed (70 ms). Claws now show from either side; Long nails stay back-side.
- DYNAMIC: `dynamic` on an item (or skin overlay) = {pivot, min, hide, only}. `fingerExtension` (0 curled .. 1 straight, from the landmarks only; thumb has its own range) scales the shape toward its pivot and hides it when the finger is curled, per finger. Long nails and Claws use it.
- GLOVE CARDS: item cards showed the item stacked on whatever was worn (so White changed when Leather was worn). A card now shows that item alone on the worn hand (`loadoutWith`).
- LENGTH-AWARE: with an extension (hotdog / longer fingers) the tip shapes of every item and overlay ride the LAST link, mid shapes fill the real tip and inner links, so hook/claws/nails/gloves no longer float mid-finger. The web follows the long finger (polyline = landmarks + link ends) and is bigger (frog/duck reach 0.93, was 0.72).
- Simplified: rings sit on base segments so are unchanged; tip-space item parts that extend past the authored length are not part of the picture-fitting bounds.

## 2026-11-02 (14) — Ad-locks only, real web membrane, fingers past the tip, Sand shed + shake-collapse (ALL VISUALS NEED SCREENSHOT / PHONE REVIEW: drawn blind, no renderer on this device)
- Changed:
  1. MONETISATION: NO MONEY ANYWHERE. Every price unlock is gone. Burning bone, Ornate ring and also Cyberpunk, Golden hand, Ruby ring and Knight glove (they were 0.99 / 0.49 too) are now ad-locks. `purchase` is no longer a valid unlock method (a file asking for it is refused), the skin/item data carries no `price`, the Store label is always "Watch ad to unlock (demo)". The unlock stub (`js/unlock.js`, STUB BOUNDARY) is still the single replaceable provider for a future ad SDK; there is no payment path at all. Confirmed by a test that scans every js/json/html file and the whole catalogue.
  2. WEBBING (frog + duck): the side fins are gone. A skin can now carry a `web` (colours, `reach`, `scallop`). `webGeometry` (js/puppet.js) builds ONE membrane per gap (index-middle, middle-ring, ring-pinky): a polygon whose two long sides are slices of the two neighbouring fingers' own landmark chains (from just past the knuckle to `reach` of the finger, following joints so a curled finger works) and whose free edge is a scallop curve (quadratic, dipping back toward the knuckles). It is computed per frame in pixel space from the landmarks, so it spans the gap however far the fingers spread and contracts when they close, with no gap. Drawn right after the palm and under every finger. The colour picker / hue-shift recolour it. No thumb web (a tucked thumb would draw a flap across the palm).
  3. FINGERS PAST THE TIP: a skin or a layer item can carry `extend` (`len` = share of the finger's length, `pieces` 1-4 links, `droop` radians, optional `fingers`). `extensionPieces` starts on the tip landmark, runs along the dip->tip direction and turns toward screen-down more and more (the steps add up to `droop`). The links are drawn with the hand's OWN mid shapes (inner links) and tip shape (last link), so the extension always matches the hand's colours, widths and recolouring. A folded finger gets a shorter extension. DRAWING ONLY: rigPlan only reads the landmarks (tests check they are unchanged, 21 points), and gestures.js never touches the rig, so finger counting is untouched. HOTDOG (`floppy`): fat links, `len 0.95, pieces 3, droop 1.35` (about as long again as the real finger, sagging). LONGER FINGERS (`longfingers`, free, in the Nail polish chip beside the other finger items): `len 0.55, pieces 2, droop 0.2` on ANY hand; it also shows when the palm faces the camera. Pictures are fitted to include the extension so it is not cropped.
  4. SAND HAND (`sand`): grainy body (dots in three sands, rough edge), one `grain` emitter that sheds a few drifting grains from around the hand (1 of 6 emitters), plus `js/sand.js`: per-hand shake detector (landmark speed in palm widths per second; collapses when speed stays over 4.5 for 0.15 s, re-forms after 0.4 s under 1.5), a 60-grain swarm that scatters/falls/wobbles while the solid hand fades, and flows home as it re-forms. The swarm is counted INSIDE the 90-particle cap (shed grains are refused when list + swarm reach 90). Runs in the existing tracking loop (live camera, Profile try-on) and in the Profile preview (no real hand there, so the preview jolts the sand hand for about a second every 6 s to show it). Reduced motion: no shedding, no collapse, the static sand hand.
- WIRE DATA: NONE added. The opponent receives a still picture drawn from the sender's id + landmarks (an existing decision), so a still sand hand is what they see; the live crumble is on the sender's own screen and the Profile. A single still cannot carry velocity, and I did not add a shake flag (it would only freeze one frame as crumbled). Finger count is data, unaffected. If you want the opponent's still to show a crumbled sand hand at the snap, a validated `sh` boolean would be the cheapest way: say so.
- Verified: 311/311 tests (new tests/extensions.test.js: no price unlock exists, web membrane geometry/stretch/order/recolour, extension geometry/landmarks unchanged/hotdog/longer fingers, sand speed/collapse/reform/glitch, swarm, caps and reduced motion, no new wire data). SW restamped (`js/sand.js` and `longfingers.json` precached). NOT seen on a phone; no image renderer here.
